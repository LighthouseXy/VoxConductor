# AmbientDesk 功能分析与拓展

> 文档状态：方案基线，2026-08-26 只读核对当前仓库后更新。
>
> 适用范围：当前 ESP32-S3 桌面语音原型，以及后续语音交互能力。
> 原则：把代码事实、已有实测和未来设想分开记录；未完成内容不写成现状。

## 1. 结论摘要

AmbientDesk 当前已经跑通可用的半双工语音闭环：长按 GPIO1 实体按键开始录音，松开发送，最长 20 秒；设备把整段 PCM 及固定 `session_id`、本轮 `turn_id` 上传到 Mac 上的 FastAPI 服务。服务端对整段录音做非流式 ASR，把最终文字与 SQLite 中最近 6 轮对话一起发给 DeepSeek，拿到完整回答后启动实时 TTS；TTS 音频块通过 HTTP 流式返回，ESP32-S3 校验轮次后由 MAX98357A 播放，完成后再按同一轮次取回文字并追加到 microSD。

当前最值得优化的不是更换大模型或引入通用 Agent 框架，而是定位整段录音上传的长尾，并把一轮请求的时间点、身份和取消语义补齐。推荐依次完成：精确日志与上传优化 → 端到端 `session_id/turn_id` 和取消 → 可选的流式 ASR/VAD → 按键打断 → AEC/NS/VAD 语音打断。

端到端实时语音模型、摄像头、外设联动和任意时刻自由插话都不进入当前两周 MVP 关键路径。Web Search 可作为服务端工具拓展，但也不应阻塞上述主线。

## 3. 当前已实现方案

### 3.1 实际语音链路

```text
长按 GPIO1 开始、松开发送（当前实体按键）
  ↓
ESP32-S3 + INMP441
录制 1～20 秒、16 kHz / 16-bit / mono PCM
  ↓ 整段 HTTP POST
Mac 上的 FastAPI /audio/turn
  ↓ 保存为 latest.wav
千问 qwen3-asr-flash：整段 WAV、stream=false
  ↓ 最终识别文本只发送一次
DeepSeek deepseek-v4-flash：stream=false、完整简短回答
  ↓ 完整回答文本
千问 qwen3-tts-flash-realtime：24 kHz / 16-bit / mono PCM
  ↓ TTS 音频块经 HTTP StreamingResponse 连续下发
ESP32-S3 收到首块即播放
  ↓
MAX98357A → 4 Ω / 3 W 扬声器
```

证据与边界：

- **[代码事实]** 固件允许最长 20 秒录音：GPIO1 按住超过 500 ms 后开始，松开请求结束；录音代码至少收满约 1 秒音频才响应停止请求，达到 20 秒会自动停止。录音结束后才把整块 PCM 作为 `/audio/turn` 请求体上传。
- **[代码事实]** 服务端接受 32,000～640,000 字节的 16 kHz/16-bit/mono PCM，先生成完整 WAV，再调用 ASR；`asr_client.py` 把完整 WAV 编成 Data URL，且请求设置为 `stream: false`。
- **[代码事实]** `deepseek_client.py` 使用非流式请求，回答限制为不超过两句、适合 10 秒内朗读；当前 TTS 不会在 DeepSeek 仍生成文字时提前开始。
- **[代码事实]** 当前 TTS 已经是实时 WebSocket TTS；`app.py` 用 `StreamingResponse` 逐块返回。固件累计 16 KiB 预缓冲后开始播放，不再等待完整 PCM 下载。
- **[代码事实]** 设备以固定的 `ambient-desk-01` 作为当前 `session_id`，并为每轮生成 `turn_id`；两者随请求传给服务端，返回音频中的 `turn_id` 会由设备校验。服务端把最近 12 条消息（最多 6 轮）从 SQLite 传给 DeepSeek；目前数据库只保存 `user/assistant` 文本，不保存工具调用、取消和完整事件流。
- **[日志事实]** 2026-08-19 已在实机完成 ASR、DeepSeek、TTS 和扬声器闭环；当前流式 TTS 是该日志之后的代码进展。
- **[代码事实]** 设备当前处于半双工流程：录音结束后才请求和播放；播放期间没有为新一轮用户语音持续采集。

### 3.2 当前交互与 UI

- **[代码事实]** 固件存在主页、天气页和语音页三个常驻页面，以及 `LISTENING`、`THINKING`、`SPEAKING`、`ERROR` 四个语音覆盖状态；结束后隐藏覆盖层并回到原页面。
- **[代码事实]** GPIO1 当前同时承担页面与语音输入：短按切页，长按开始录音，松开发送。
- **[代码事实]** 成功完成一轮后，固件用固定 `session_id` 和本轮 `turn_id` 请求 `/audio/turn/{turn_id}`，取回匹配的 `transcript/answer` 并追加写入 microSD 的 `/sdcard/conversations.txt`。文本文件当前只写时间、用户文本和回答，没有写入 `session_id/turn_id` 或同步状态。
- **[代码事实]** 已有“语音系统未就绪”和“已有一轮进行中”的保护，能避免重复创建本地语音任务。
- **[部分实现]** `session_id/turn_id` 已贯穿语音上传、音频响应校验和按轮次取回文本，但 `session_id` 仍为单设备固定值，也没有取消、旧轮迟到数据丢弃或重连恢复。
- **[未实现]** 播放取消、唤醒词、VAD、AEC 和真正的 barge-in 均未在当前代码中出现。

这里的四个语音覆盖状态只是流程反馈，不等于完整产品 UI，也不代表已经实现自动起止检测或语音打断。

以下是引入可变时长录音前的历史样本，用于理解旧延迟构成，不代表 2026-08-22 当前录音方式。当前版本应按录音实际时长重新建立基线。

| 阶段 | 已有数据 | 当前计时含义 | 结论 |
| --- | ---: | --- | --- |
| 固定录音 | 3.00 s | 设备本地固定窗口 | 每轮必付，且短问题也必须等满 |
| 录音上传 | 未单列 | 服务端 `turn_started` 在读取请求体前设置，理论上计入服务端总计的一部分 | **[待验证]** 需设备与服务端双端时间点 |
| ASR | 约 0.60 s | `transcribe_audio()` 整体调用 | **[已有实测]** 单轮样本 |
| DeepSeek | 约 1.36 s | 完整非流式回答调用 | **[已有实测]** 单轮样本 |
| TTS 首包 | 约 0.24 s | 当前回调计时从 TTS 连接和会话更新完成后开始，到首个音频回调 | **[已有实测]** 不含连接建连时间 |

| 服务端总计 | 约 5.17 s | 从服务端开始接收本轮请求，到 TTS 生成器结束 | **[已有实测]** 可能受 HTTP 下发和设备播放背压影响 |

上述数字来自已有一次实测描述；本次在仓库中只找到计时代码，没有找到这组原始控制台输出。它们适合作为优化起点，不应当作稳定性能指标。

### 4.2 尚未细分的约 2.16 秒

按当前日志口径：

```text
5.17 - 0.60 - 1.36 - 1.05 = 2.16 秒
```

这约 2.16 秒尚未被现有日志拆开，可能包括：请求体接收、WAV 写盘、线程调度、ASR/LLM 调用外围开销、TTS WebSocket 建连与会话设置、HTTP 分块传输、设备同步播放造成的背压，以及清理关闭。具体占比均为 **[待验证]**，不能凭差值直接归因给网络或某一家云服务。

历史版本中，用户按键到本轮服务端流结束的粗略时间至少约为 `3.00 + 5.17 = 8.17 s`；其中播放与 TTS 下发部分重叠，所以这不是“等待首声”的时间，也不是当前可变时长版本的性能指标。

### 4.3 下一步应增加的时间点

**[后续方案]** 先记录最少但足够定位问题的一组时间点：

1. 设备：按键、录音首样本、录音末样本、上传开始、收到 HTTP 首字节、首个 PCM 送入 I2S、播放完成。
2. 服务端：请求头到达、请求体读完、WAV 写完、ASR 请求/首个结果/最终结果、DeepSeek 请求/完整结果、TTS 连接完成、首个音频块、最后音频块、响应结束。
3. 每条记录带同一个 `session_id` 和 `turn_id`，使用单调时钟计算耗时；跨设备只比较事件顺序，除非已校准时钟。
4. 连续测试至少 10 轮，保留中位数和 P90；区分“按下到首声”与“按下到播放结束”。

## 5. 流式录音、流式 ASR 与 VAD

### 5.1 正确概念

**[后续方案]** 流式链路应把麦克风音频按约 20–100 ms 的小块持续发给服务端或流式 ASR，而不是先在 ESP32-S3 中积累完整一轮录音。ASR 可以边接收边返回临时文本，例如：

```text
临时：今天上...
临时：今天天气...
最终：今天天气怎么样？
```

VAD 用来判断何时真正开始说话、何时连续静音足够长而结束一轮。只有最终完整文本才发送一次给 DeepSeek。临时文本可以用于 UI 反馈或提前准备，但不能把一句问题拆成多次独立的 DeepSeek 请求，否则会造成重复回答、上下文混乱和额外费用。

### 5.2 推荐的近期数据流

```text
设备持续产生 20–100 ms PCM 小块
  → 服务端 VAD + 流式 ASR
  → 临时文本仅用于界面/调试
  → VAD 判定结束
  → ASR 最终文本
  → DeepSeek 只调用一次
  → 完整回答进入流式 TTS
```

**[待验证]** 具体 ASR 供应商及其流式接口、端点检测能力、音频编码、超时和费用，需要按当时可用的官方接口另行确认。近期不必同时在设备端和服务器端实现两套 VAD；先以服务器 VAD 为单一结束判定，设备端只做采集、分块和基本超时保护。

## 6. 类 ChatGPT 语音体验所需能力

这些能力不是一个开关，而是按依赖关系逐层组成：

| 能力 | 作用 | 当前状态 | 关键风险 |
| --- | --- | --- | --- |
| 自动讲话起止检测 | 不再固定录 3 秒 | 未实现 | 环境噪声下误开始、误结束 |
| VAD | 判断语音和静音区段 | 未实现 | 阈值、静音尾长和远场表现需实测 |
| 唤醒词（可选） | 降低常开误触发和隐私顾虑 | 未实现 | 模型资源、误唤醒、与 VAD/AEC 的组合成本 |
| barge-in | AI 播放时用户开口即可打断并开始新轮 | 未实现 | 扬声器回声会被误认为用户讲话 |
| 取消旧 TTS | 停止服务端继续合成和下发 | 未实现 | SDK/连接取消是否及时 **[待验证]** |
| 清空本地播放缓冲 | 打断后扬声器立即停止旧回答 | 未实现 | I2S DMA、HTTP 回调和任务并发需统一停机顺序 |
| `session_id/turn_id` | 识别当前会话和轮次 | 基础请求、响应校验和数据库保存已接入 | 固定会话、多设备、重启、取消和迟到数据规则仍待完善 |
| 丢弃迟到数据 | 防止旧文本或旧音频在新轮中复活 | 未实现 | 设备与服务端都必须校验轮次 |

建议语义：`session_id` 标识一次会话或一次设备在线周期；`turn_id` 在该会话内单调递增。任何 ASR、DeepSeek、TTS 音频块、完成事件和错误都必须携带二者。设备只播放当前轮的数据；开始新轮或取消后，旧轮即使晚到也直接丢弃。

## 7. 真正语音打断的约束

### 7.1 为什么只有 VAD 不够

真正的 barge-in 要求 AI 播放期间仍持续采集麦克风。桌面设备的扬声器距离麦克风很近，麦克风会录到正在播放的 TTS；如果直接对原始麦克风信号做 VAD，AI 自己的声音很可能触发“用户开始讲话”。

因此通常需要：

1. AEC：用正在播放的数字音频作为远端参考，消除麦克风中的扬声器回声；
2. NS：压低稳定环境噪声；
3. VAD：在 AEC/NS 后判断是否有人真正开口；
4. 打断控制：取消旧 TTS、关闭旧 HTTP/流连接、清空本地播放缓冲，再创建新 `turn_id`。

### 7.2 当前采样率冲突

- **[代码事实]** INMP441 录音链路是 16 kHz。
- **[代码事实]** 当前 TTS 和 MAX98357A 播放链路是 24 kHz。
- **[官方约束]** ESP-SR 当前 ESP32-S3 AEC 直接接口只支持 16 kHz，且需要麦克风输入和扬声器播放参考信号。参考：[Espressif ESP-SR AEC 文档](https://docs.espressif.com/projects/esp-sr/en/latest/esp32s3/acoustic_echo_cancellation/README.html)。

因此接入 ESP-SR AEC 前必须统一 AEC 域的采样率和时间轴。优先顺序是：

1. **优先验证 TTS 直接输出 16 kHz PCM**：链路最简单，麦克风、AEC 参考和播放统一为 16 kHz；但当前 TTS SDK 是否支持、音质是否可接受为 **[待验证]**。
2. 如果继续播放 24 kHz，则从实际送往扬声器的 PCM 生成严格同步的 16 kHz 参考信号，做 24→16 kHz 重采样后送给 AEC。重采样滤波、缓冲延迟和参考/麦克风对齐都需要实机标定。

AEC 不是只加一个组件即可完成。扬声器音量、箱体结构、麦克风位置、播放到采集的延迟、PSRAM/CPU 占用和双 I2S 调度都会影响效果。ESP-SR 版本和具体 AEC/AFE 模式也应在实施时锁定并重新核对，而不是直接照用示例默认值。

## 8. 方案比较

| 方案 | 主要收益 | 复杂度 | 主要风险 | 是否保留 DeepSeek | 建议 |
| --- | --- | --- | --- | --- | --- |
| 固定 3 秒录音（历史） | 最容易复现和排障 | 低 | 固定等待、说不完或空白过多、不能自然连续对话 | 是 | 已被可变时长方案替代，只保留概念回归基线 |
| 长按说话、松开发送（当前） | 已去掉固定 3 秒，对噪声不敏感，最长可录 20 秒 | 低 | 整段录完后才上传；必须持续按住；按键手感和最长时长需实机确认 | 是 | 当前 V1 可用基线 |
| 流式 ASR + 服务器 VAD | 自动结束、降低短句等待、可显示临时文本 | 中 | WebSocket/长连接、断线、VAD 参数和供应商接口差异 | 是 | **近期主线，优先推荐** |
| 按键打断 | 先验证取消、轮次隔离和缓冲清理，不需解决回声 | 中 | 取消不彻底会复播旧音频；需定义短按/长按在播放中的行为 | 是 | **AEC 前必须完成的控制面验证** |
| 全双工 AEC + NS + VAD 语音打断 | 最接近自然语音助手，可在播放中开口 | 高 | 回声、采样率、同步、声学结构、CPU/内存和误触发 | 是 | 中长期，在取消机制稳定后实施 |
| 端到端实时语音模型 | 潜在更低延迟、更自然的语音语调和轮次控制 | 很高 | 供应商锁定、持续连接成本、可控性、工具调用和隐私；可能重写现有链路 | 通常不直接保留；若再调用 DeepSeek 会增加编排与延迟 | 仅做独立实验，不进当前 MVP |

明确推荐：近期继续保留 DeepSeek 作为唯一文本回答模型，不要同时更换 ASR、LLM、TTS 和交互协议。先解决输入结束判定与取消一致性，收益更直接，也更容易判断每次改动是否有效。

## 9. 推荐阶段顺序

### A. 增加精确时间点日志

目标：把 2.16 秒未知开销拆开，并建立“按下到首声”的基线。只改计时和关联字段，不先改模型。

验收：同一轮能在设备与服务端按 `session_id/turn_id` 对齐；至少 10 轮有中位数和 P90。

### B. 在当前可变录音基线上评估流式 ASR + 服务器 VAD

目标：20–100 ms 音频分块上传，自动识别讲话起止；最终文本只调用一次 DeepSeek。

验收：不再需要第二次按键提交，长句在上限内不会截断；临时文本不会触发多次回答；断线或长时间静音能超时回到 HOME。

### C. 完善 `session_id/turn_id` 并加入取消机制

目标：为后续打断提供可靠控制面。取消必须覆盖 ASR、DeepSeek、TTS、HTTP 下发和设备播放，不能只隐藏 UI。

验收：取消后旧轮音频不再播放；新轮开始后，任何旧轮迟到数据均被两端丢弃。

### D. 先用按键验证打断

目标：播放中按键立即停止当前回答并开始或准备新一轮，先验证取消顺序、I2S 缓冲清理和轮次切换。

验收：按键后扬声器快速静音，旧 TTS 不复播；连续多次打断不死锁、不泄漏任务或连接，并且不破坏 GPIO1 已有的短按切页、长按说话语义。

### E. 最后接入 ESP-SR AEC 实现语音打断

目标：播放时持续采集，使用同步播放参考做 AEC，再接 NS/VAD 检测用户开口，并复用阶段 C/D 的取消机制。

验收：仅播放 AI 声音不会自触发；用户在近场与目标距离开口能稳定打断；不同音量和典型房间环境下记录误触发/漏触发率。先验证 16 kHz 全链路，再决定是否值得保留 24 kHz 播放和重采样。

## 10. Web Search 工具拓展

DeepSeek 或其他文本模型通常不会因为用户问“今天的新闻/天气”就自动获得实时互联网内容。**[后续方案]** 应由 Mac 服务端负责工具编排：

```text
最终 ASR 文本
  → 判断是否确实需要实时信息
  → 需要时调用搜索/API
  → 筛选少量可信结果并附来源、时间
  → 连同结果只调用一次 DeepSeek
  → TTS
```

只应选择性触发搜索；闲聊、设备控制和已有上下文问题不搜索。主要代价是额外延迟、搜索/API 费用、错误或过时来源、提示注入和模型对来源的误读。服务端需要来源白名单或可信度策略、超时、结果数量限制，以及“搜索失败时明确说明无法获取实时信息”的降级行为。

Web Search 不进入当前两周 MVP 关键路径。应在阶段 A–D 稳定后，以一个窄场景（例如天气或新闻）验证，而不是先搭建通用多工具框架。

## 13. DeepSeek Harness 评估（截至 2026-08-22）

### 13.1 定位与官方证据

DeepSeek Harness（`dsh`）是 DeepSeek AI 官方开源的 Agent Harness，不是新的大模型、ASR/TTS 服务，也不是面向 ESP32 的固件框架。官方将其描述为“everything is a plugin”的可组合运行时，并明确标注为 **Developer Preview**，当前会快速迭代且可能出现破坏兼容性的改动。参考：[官方仓库与 README](https://github.com/deepseek-ai/deepseek-harness)。

从官方架构看，它围绕以下能力组织 Agent：

- 追加式 `SessionEvent` 会话日志，并从日志派生模型上下文；
- system prompt 与工具 schema 的组装；
- 带执行守卫的工具注册和调用管线；
- 一轮中允许“模型请求 → 工具调用 → 工具结果 → 下一模型步骤”的 Agent Loop；
- Agent 生命周期、状态、取消和恢复；
- 模型适配器、持久化、审批、沙箱和遥测等可替换插件。

官方说明见 [架构文档](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md) 与 [Core 子系统](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/core.md)。官方也提供 Python SDK；SDK 会启动配套运行时，通过同一 Harness 实例和相同 `session_id` 延续持久会话。其入门示例主要面向可修改隔离工作区的编码任务，默认示例工具是持久 Bash 与文本编辑器，而不是语音助手领域工具。参考：[Python SDK 指南](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/user/guide/python-sdk.md)。

因此，对 AmbientDesk 更准确的定位是：它可能替代或补充 **Mac 服务端的 Agent 编排层**，不能替代设备音频链路。

### 13.2 当前链路与可插入位置

当前代码实际链路为：

```text
ESP32-S3 整段录音
  → FastAPI /audio/turn
  → qwen3-asr-flash 非流式 ASR
  → SQLite 按设备传入的固定会话读取最近 12 条消息
  → deepseek-v4-flash 非流式回答
  → SQLite 原子保存 user/assistant 本轮文本
  → qwen3-tts-flash-realtime
  → HTTP StreamingResponse
  → ESP32-S3 + MAX98357A 播放
```

现有服务器已经拥有一个轻量会话层，而不是完全无状态：

- `conversation_store.py` 用 SQLite 保存 `session_id/turn_id/role/content`；
- 当前设备会话固定为 `ambient-desk-01`；
- 每轮从数据库读取最多 12 条消息，即最多 6 轮上下文；
- 设备生成 `turn_id`，服务端按 `session_id/turn_id` 保存，并在响应中返回供设备校验；
- 没有工具调用记录、运行步骤、取消状态、迟到数据判定或上下文压缩。

Harness 的合理插入点位于 ASR 最终文本之后、TTS 之前：

```text
                    ┌─ 快路径：现有 DeepSeek + SQLite ─────────┐
ASR 最终文本 → 路由器                                      → TTS
                    └─ Agent 路径：Harness → 工具 → 最终回答 ─┘
```

不应把 Harness 放进 ESP32，也不应让它直接拥有 I2S、LVGL 或 SD 卡硬件。

### 13.3 对具体功能的实际价值

| 功能 | Harness 能提供的价值 | 仍需 AmbientDesk 自己完成 |
| --- | --- | --- |
| 多轮上下文 | 用事件日志统一记录用户消息、模型消息、工具调用和结果；支持恢复、回放和派生上下文 | 设备身份到 `session_id` 的映射、上下文保留策略、摘要/压缩规则、旧数据库迁移 |
| 工具调用 | 提供工具 schema、注册、执行守卫和多步骤 Agent Loop | 定义天气、搜索、提醒、会话检索等领域工具；参数校验、超时、错误语义和幂等性 |
| 联网搜索 | 官方能力图中存在 Web provider seam 及多种搜索 provider 包，可作为工具接入 | 选择和配置搜索供应商、凭据、来源策略、引用格式和失败降级；不能假设默认配置已自动开启搜索。参考：[Capability seams](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/capability-seams.md) |
| SD/会话整理 | Agent 可判断何时检索、筛选、摘要和生成任务清单 | Mac 无法凭空读取 ESP32 的 microSD；需由设备上传文本、服务端数据库作为主存储，或新增受限的 SD 同步协议 |
| 提醒 | Agent 可把自然语言转换为结构化提醒参数并调用工具 | 独立调度器、持久化、时区、重启恢复、通知投递、删除/修改和重复提醒语义 |
| 取消/打断 | Agent handle 有取消活动与清理待处理输入的接口，可终止服务器端 Agent 活动 | ASR/TTS SDK 是否可及时取消、HTTP 连接终止、ESP32 清空 I2S DMA、本地静音和旧 `turn_id` 丢弃；Harness 取消不等于语音 barge-in |
| 可观测性 | 持久记录 turn/step、模型流、工具调用和结果，便于重放和定位错误 | 跨设备统一 `session_id/turn_id`、音频阶段时间点、脱敏、日志保留和指标汇总 |

### 13.4 它不能替代的部分

以下能力仍属于 AmbientDesk 固件、音频服务或供应商适配层：

- INMP441 采集、MAX98357A 播放和 I2S 资源切换；
- ST7789/LVGL UI 与设备状态机；
- ASR、TTS、VAD、AEC、NS 和唤醒词模型；
- 录音分块、HTTP/WSS 音频协议和播放缓冲；
- 扬声器播放期间检测用户开口的声学处理；
- microSD 挂载、读写、拔卡和断电恢复；
- Wi-Fi 断线恢复以及设备端迟到音频丢弃。

尤其要区分两类“取消”：Harness 可以取消服务器上的 Agent 活动，但自然语音打断还要求 ESP32 立刻停止旧音频、服务端停止旧 TTS、两端拒收旧轮数据；若要在扬声器播放时靠说话触发打断，还需要 AEC + VAD。Harness 不解决这些声学问题。

### 13.5 适用与不适用场景

适合进入 Agent 路径的请求：

- “搜索今天杭州天气和空气质量，再结合我的日程给建议”；
- “整理最近一周的对话，列出未完成任务”；
- “查找我之前提到过但还没购买的器件”；
- “把明天下午三点开会写成提醒”；
- “比较多个来源后给出带出处的结论”。

不适合默认进入 Agent 路径的请求：

- “你好”“你是谁”等简单闲聊；
- 仅依赖最近上下文的追问；
- 读取本机已经拥有的时间、音量或状态；
- 对低延迟要求高、无需工具的一问一答；
- 仍处于 ASR/VAD/播放错误排查阶段的基础回归测试。

V1 不应为了“以后也许需要”而增加多 Agent、子 Agent、自修改插件、Shell、任意文件编辑或通用工作流。这些能力扩大故障面和安全边界，对当前桌面语音 MVP 没有直接收益。

### 13.6 三种方案比较

| 方案 | 优点 | 代价与风险 | 适合阶段 |
| --- | --- | --- | --- |
| 继续自研轻量编排 | 与现有 FastAPI/SQLite 一致；依赖少；延迟和行为容易控制；最容易逐步加天气、会话检索等窄域工具 | 工具增多后会重复实现 schema、权限、重试、事件日志、取消和上下文压缩；长期维护成本会上升 | **V1 推荐** |
| 全面引入 Harness | 会话事件、工具管线、Agent Loop、取消、插件和可观测性更系统；复杂任务扩展快 | Developer Preview 兼容风险；引入配套运行时/JSON-RPC；默认示例偏编码 Agent；迁移现有 SQLite 与接口成本高；普通问答也可能承受额外延迟 | 当前不推荐；仅当复杂工具成为主体后重评 |
| 双路径混合 | 简单对话保留低延迟，复杂任务使用 Harness；可逐项实验并随时回退 | 路由器、双会话存储和结果归一化会增加边界；必须避免同一轮在两条路径重复保存或失序 | **V1.5 推荐候选** |

明确建议：

1. **V1：继续自研轻量编排。** 稳定现有可变时长录音和 microSD/SQLite 文本记录，完成延迟拆解、轮次协议完善与取消。摄像头、泛化外设联动和任意语音自由插话不进入关键路径。
2. **V1.5：验证双路径。** 只把一个只读场景接入 Harness，例如“检索并整理近期会话”或“查询天气并给建议”；简单聊天继续走现有链路。
3. **后续探索：视证据决定是否扩大。** 只有当领域工具数量明显增加、现有编排代码开始反复实现相同基础设施，并且 Harness 的延迟和稳定性达到门槛时，才考虑让更多复杂任务迁移。

### 13.7 延迟、复杂度和兼容风险

Harness 不一定让单轮回答更快。复杂 Agent 请求通常会增加：

1. 请求路由或意图判断；
2. 一次模型决策；
3. 一个或多个工具网络请求；
4. 把工具结果交给模型继续生成；
5. 结果整理和 TTS。

若通过 Python SDK 接入，官方实现会驱动配套运行时；因此需要分别测量冷启动、热启动、JSON-RPC 往返和常驻内存。生产形态必须复用长期运行的 Harness 实例，不能每个语音轮次启动一次进程。

当前兼容风险包括：

- 官方明确处于 Developer Preview，存在破坏兼容性改动；
- 当前服务使用 Python 3.14 虚拟环境，虽然官方文档写 Python 3.10+，仍需实测对应 wheel/runtime 在本机的兼容性；
- Python SDK 示例面向隔离工作区和编码工具，不等于已经具备 AmbientDesk 的语音事件、提醒和 SD 接口；
- 若 Harness 和现有 SQLite 同时保存同一会话，可能出现重复记录、顺序不一致和两个上下文事实源；
- Agent 工具结果可能很长，直接送入模型与 TTS 会增加 token、延迟和朗读时长。

控制方式：锁定精确版本；通过独立适配模块隔离 Harness；保留功能开关和现有快路径；升级前回放固定测试集；不得在 V1 直接迁移唯一可用链路。

### 13.8 安全边界

官方 Python 示例明确使用可修改隔离工作区，并暴露持久 Bash 与文本编辑器；文档还提醒其示例文件系统可访问运行时进程所能看到的绝对路径。因此不能把该默认示例直接用于 AmbientDesk 主服务。

若实验接入，首版安全边界为：

- 不挂载 Bash、任意文件编辑、子 Agent或自修改工具；
- 只注册 AmbientDesk 专用的少量工具，并默认只读；
- 会话搜索工具只能访问当前设备/用户授权的 `session_id`；
- SD 工具只能访问专用同步目录，禁止任意路径；
- Web 内容一律按不可信输入处理，限制长度和来源，避免网页提示注入改变系统规则；
- 创建、删除、发送、购买和设备控制等写操作必须二次确认，并使用幂等键；
- 每个工具设置参数 schema、超时、结果大小、调用次数和审计日志；
- API Key 留在服务端环境变量，不写入固件、会话日志或工具返回。

### 13.9 最小隔离评估实验

本实验不修改固件、不替换 `/audio/turn`，只建立服务器旁路探针：

```text
固定文字测试集
  → 独立 Harness 进程/SDK 适配器
  → 仅一个只读工具（优先：会话检索）
  → 返回最终文字和事件记录
  → 与当前 SQLite + DeepSeek 路径对比
```

建议测试集至少包括：

- 10 条无需工具的问题：检查是否错误调用工具及额外延迟；
- 10 条必须调用工具的问题：检查工具选择和参数正确率；
- 5 条工具超时/空结果/错误问题：检查降级表达；
- 5 条取消、恢复同一 `session_id`、新建会话问题：检查隔离和恢复；
- 注入型网页或恶意记录样本：检查是否越权调用写工具。

记录指标：

| 指标 | 目的 |
| --- | --- |
| 冷启动与热启动耗时 | 判断运行时应否常驻 |
| 首个可朗读文本时间 | 衡量语音体验，而不是只看最终完成时间 |
| 总耗时 P50/P90 | 识别不稳定长尾 |
| 每轮模型请求和工具调用次数 | 估算延迟与费用 |
| 工具选择正确率、参数正确率 | 判断 Agent 是否真正提升能力 |
| 无需工具时的误调用率 | 防止简单请求变慢 |
| 搜索答案来源覆盖率与引用有效率 | 约束实时信息质量 |
| 取消到停止的时间、取消后旧结果出现次数 | 验证取消语义 |
| 会话恢复正确率、跨会话串话次数 | 验证上下文隔离 |
| 进程常驻内存、CPU 和崩溃恢复 | 判断 Mac/未来服务器部署负担 |

建议采用门槛（属于评估标准，不是已实现指标）：

- 快路径的首声 P90 不因 Harness 实验而退化超过 200 ms；
- 无需工具问题误调用率低于 5%；
- 只读工具任务成功率至少 90%，且不得发生跨会话数据泄漏；
- 取消后的旧 Agent 结果不得进入新 `turn_id` 或继续触发 TTS；
- Harness 版本升级后固定回放集无阻断性回归，否则继续锁定版本或回退。

### 13.10 采用与不采用门槛

满足以下条件时，可把 Harness 作为 V1.5 的复杂任务引擎：

- 至少出现 3 个稳定、边界明确的领域工具，现有手写编排开始重复实现工具循环、权限和事件记录；
- Python SDK/运行时在目标 Mac 或服务器连续运行稳定；
- 会话存储的单一事实源已经确定，能从现有 SQLite 平滑映射或迁移；
- 旁路实验达到工具正确率、延迟、取消和隔离门槛；
- 仅启用最小工具集，且可通过功能开关立即回退到现有链路。

出现以下任一情况时，不应采用或扩大使用：

- 当前主要问题仍是录音截断、上传长尾、VAD、播放或断线恢复；
- 只有一个简单天气/API 工具，普通函数调用已经足够；
- 需要依赖 Bash 或宽泛文件权限才能完成日常语音任务；
- 热路径首声或 P90 延迟明显恶化；
- Developer Preview 升级频繁破坏适配层；
- 无法实现可靠的 `session_id/turn_id` 隔离和取消。

### 13.11 建议实施顺序

1. 保持现有 FastAPI + SQLite + DeepSeek 路径可回归，不安装 Harness。
2. 先完成当前 V1：稳定可变录音时长、上传长尾定位、轮次协议完善、取消、SD 文本记录和连续多轮测试。
3. 把现有会话层抽象成窄接口，明确 SQLite 是唯一事实源，或明确迁移策略。
4. 先用普通 Python 函数实现一个只读领域工具，验证工具输入输出和失败语义。
5. 在独立虚拟环境/进程建立 Harness 旁路探针，只用固定文字和测试数据库，不接 ESP32 实机请求。
6. 完成第 13.9 节测试并保存冷/热延迟、正确率、取消和资源数据。
7. 若达标，增加显式路由器：普通对话走快路径，复杂任务走 Agent 路径；两条路径统一返回可朗读短文本。
8. 最后才评估 Harness 文本增量事件如何衔接 TTS；在确认 Python SDK/JSON-RPC 能可靠提供所需增量事件前，不承诺“边思考边朗读”。
9. 多 Agent、通用 Web Search、自修改和泛化外设控制只作为后续独立探索，不进入两周 MVP。

## 14. SD 卡、服务端上下文与 Agent 数据协作

### 14.1 当前实现与边界

当前数据链路不是“Agent 从 SD 卡读取历史”，而是“服务端先完成对话并保存，设备随后保存一份本地副本”：

```text
ESP32 语音请求（session_id + turn_id）
  → 服务端 ASR / DeepSeek / TTS
  → SQLite 原子保存 user + assistant
  → ESP32 按 session_id + turn_id 取回本轮文字
  → 追加写入 /sdcard/conversations.txt
```

- **[代码事实]** `server/conversation_store.py` 使用 SQLite `messages` 表保存 `session_id`、`turn_id`、`role`、`content` 和创建时间。生成回答前，服务端读取该会话最近 12 条消息，即最多 6 轮，作为当前在线对话上下文。
- **[代码事实]** ESP32 在成功播放一轮后请求 `/audio/turn/{turn_id}`；服务端同时按 `session_id/turn_id` 查找对应记录，设备再把时间、用户文本和回答追加到 `/sdcard/conversations.txt`。
- **[代码事实]** SD 卡挂载或写入失败不会推翻已完成的云端语音回答；当前没有 SD 同步游标、ACK、补传队列、远程文件接口或设备侧 WebSocket。
- **[代码事实]** 当前服务端模型链路以及未来可能接入的 Agent 都不能通过 Wi-Fi 任意浏览或读取设备 SD 卡。ESP32 没有暴露文件列表/读取接口，Mac 服务端也没有设备发现和远程存储客户端。
- **[架构结论]** 每轮在线语音本来就先经过服务端并写入 SQLite，因此连续对话不需要再从 SD 卡读取同一份记录。把这份副本重新送回模型只会增加重复、冲突和延迟。
- **[后续方案]** 实时上下文应优先来自服务端：最近轮次、滚动摘要、用户偏好、任务记忆和必要的工具结果。当前只实现了“最近 6 轮”，摘要、偏好和任务记忆尚未实现。

当前 `/sdcard/conversations.txt` 是设备侧追加归档，可视为本地副本和离线备份，但它还不是可恢复的同步队列。并且当前语音依赖服务端 ASR、DeepSeek 和 TTS；设备断网时无法完成一轮云端对话，所以“断网对话补传”属于未来能力，而不是当前行为。

### 14.2 推荐职责划分

| 组件 | 推荐职责 | 不应承担 |
| --- | --- | --- |
| 服务端 SQLite | 在线会话、Agent 上下文和同步去重的事实源 | 依赖设备在线才能恢复最近上下文 |
| ESP32 SD 卡 | 本地归档、未来离线待同步队列、资源文件、运行日志和备份 | 作为实时对话上下文的唯一事实源 |
| 服务端 Agent | 使用最近轮次、滚动摘要、用户画像/偏好和任务记忆；按需调用受限工具 | 任意浏览整个 SD 文件系统或直接操作原始路径 |
| 同步协议 | 在 SQLite 与 SD 卡之间交换明确用途的数据，并负责身份、幂等、ACK 和重试 | 把设备文件系统直接暴露成无边界网络磁盘 |

推荐架构可以概括为：

> **服务端 SQLite 保存在线上下文，SD 卡保存本地归档和断网队列，两者通过明确的增量同步协议协作。**

如果以后引入 Agent 事件存储或更换数据库，应继续保持一个明确的服务端事实源；不能让 SQLite、Harness 会话日志和 SD 卡各自独立决定“哪段历史是真的”。

### 14.3 SD 卡对 Agent 的合理价值

SD 卡更适合以下用途：

1. **设备断网时的待同步队列**：缓存未来能够在离线状态产生的设备事件、短指令、诊断数据或对话记录，恢复网络后补传。**[后续方案]**
2. **本地完整对话归档**：保留用户可见、可导出的设备侧副本。当前已有简单文本追加记录，但没有轮转、检索和同步状态。
3. **UI 与音频资源**：天气图标、背景图、提示音、离线语音包等不需要每次从网络下载的文件。**[后续方案]**
4. **运行日志与故障诊断**：保存重启原因、网络失败、音频错误、同步失败等有限且可轮转的诊断信息。**[后续方案]**
5. **配置或记忆备份**：保存服务端生成的 `summary.json`、`memory.json` 等可恢复副本；在线使用时仍由服务端版本和同步协议决定有效性。**[后续方案]**
6. **用户可携带的数据副本**：用户可以取出 SD 卡人工查看或备份；需要同时考虑明文对话的隐私风险。

SD 卡不适合作为 Agent 每次回答前必须读取的数据库：它可能未插入、损坏、正在写入或与服务端版本不同，而且远程读取会把设备在线状态和局域网质量加入语音关键路径。

### 14.4 服务端访问 SD 数据的四种方案

| 方案 | 适用性 | 复杂度 | 主要风险 | 推荐阶段 |
| --- | --- | --- | --- | --- |
| A. ESP32 主动增量同步 | 最符合当前“设备主动连接 Mac 服务端”的方向，不要求固定设备 IP | 中 | 幂等、游标持久化、断线重试、SD 并发读写 | **优先，V1 后续** |
| B. ESP32 提供受限 HTTP 接口 | 适合局域网临时诊断或按需取少量文件 | 中～高 | IP 发现、同网限制、认证、路径安全、设备离线 | 非主方案，按明确场景评估 |
| C. 设备主动建立长期 WebSocket | 双向命令和数据通道扩展性最好 | 高 | 协议状态、并发、重连、取消、迟到响应 | **V2 候选** |
| D. USB Mass Storage | 人工导出直观，不依赖网络 | 中 | 电脑与 ESP32 同时访问 FAT 可能损坏文件系统 | 只作人工维护，不作 Agent 在线通道 |

#### 方案 A：ESP32 主动增量同步（推荐优先）

设备定期或在产生待同步记录后主动调用类似接口：

```http
POST /device/sync/conversations
```

建议流程：

1. ESP32 只读取并批量上传尚未确认的记录；
2. 服务端按唯一 `record_id` 幂等写入，重复上传不产生重复数据；
3. 服务端返回已接受记录或高水位 ACK；
4. 设备持久化同步游标；
5. 断网时继续追加本地数据，恢复后从游标继续补传。

它适合当前设备主动发起 HTTP 请求的架构，也不依赖服务端知道 ESP32 的局域网 IP。需要注意：当前在线语音记录已经先写入 SQLite，不能把 SD 中的镜像记录无条件再插入一次。增量同步首先服务于未来的离线/设备侧数据；若用于对账，应通过相同 `record_id` 或 `session_id + turn_id` 去重。

#### 方案 B：ESP32 提供受限 HTTP 接口

可设计窄接口，例如：

```text
GET /storage/files
GET /storage/conversations?after=...
GET /storage/file?name=...
```

该方案允许服务端按需读取，但必须解决：

- ESP32 IP 地址发现或 mDNS；
- 设备与服务端位于同一可互访网络；
- 设备离线、休眠或重连后不可访问；
- 大文件分块、范围请求和限速；
- 只允许预定义逻辑文件名，不能接受任意相对/绝对路径；
- 录音、写日志、同步与远程读取之间的 SD 访问互斥；
- 设备身份认证、请求签名或短期令牌；
- 响应大小、并发数和请求频率限制。

它不适合作为当前在线上下文主链路，更适合未来的局域网诊断或明确文件导出功能。

#### 方案 C：设备主动建立长期 WebSocket

ESP32 主动连接服务端后，服务端可通过受限消息发送：

```text
storage.list
storage.read
conversation.sync
memory.update
```

协议至少需要 `request_id`、`session_id`、消息类型、分块序号、ACK、超时、取消、断线重连、迟到数据丢弃和 SD 文件访问互斥。还要规定命令权限、最大响应大小、并发上限，以及设备重启后哪些请求可以恢复。

该方案能继续扩展到资源更新、日志获取和设备控制，但协议与并发复杂度明显高于当前 HTTP 单轮请求，适合作为 V2 的统一设备通道，不应为了读取一个文本文件提前引入。

#### 方案 D：USB Mass Storage

USB MSC 可以让电脑像读取 U 盘一样读取 SD 卡，适合用户人工导出归档或维护资源。它不适合作为在线 Agent 的自动数据通道，也不应在 ESP32 仍挂载并写入同一 FAT 文件系统时让电脑同时读写。若未来实现，必须采用明确的独占切换：进入 MSC 模式前由 ESP32 停止文件访问并卸载，退出后再重新挂载。

### 14.5 推荐记录格式与同步语义

**[后续方案]** 简单文本可以逐步升级为追加式 `conversations.jsonl`。每行是一条完整且独立的 JSON 记录，例如：

```json
{"record_id":"ambient-desk-01:20260826-42","session_id":"ambient-desk-01","turn_id":"20260826-42","timestamp":"2026-08-26T21:35:12+08:00","user":"明天会下雨吗？","assistant":"明天有阵雨，出门建议带伞。"}
```

最低字段包括：

- `record_id`：全局或设备范围内唯一，供幂等去重；
- `session_id`：归属的设备/用户会话；
- `turn_id`：对话轮次；
- `timestamp`：带时区的事件时间；
- `user`：最终识别文本；
- `assistant`：最终回答文本；
- `sync_status` 或独立同步游标。

JSONL 应保持追加式。与其反复修改历史行中的 `sync_status`，更推荐把“最后已确认的 `record_id`/偏移量”单独保存在可靠的同步游标中；只有服务端 ACK 成功后才推进游标。具体放在 NVS 还是 SD 检查点文件，需要结合断电恢复测试决定。

同步协议还必须覆盖：

- 唯一记录 ID、幂等写入和重复数据去重；
- 游标或逐批 ACK；
- 有上限的批量上传、断线退避与重试；
- JSONL 文件大小限制、轮转和磁盘余量保护；
- SD 读写互斥，避免归档、同步和资源读取同时操作同一文件；
- 请求大小、单次记录数、速率和并发限制；
- 文件/资源类别白名单，禁止任意路径访问；
- 写入失败、卡拔出、文件损坏和部分写入的恢复；
- 服务端生成内容同步回设备时的版本号、校验和与原子替换；
- 对话和用户偏好是否加密、保留多久、如何由用户清除。

### 14.6 分阶段规划

#### V1

- **[已实现]** 保留 `/sdcard/conversations.txt` 本地追加归档；SD 失败不阻断在线语音。
- **[优先完善]** 继续以 SQLite 最近轮次作为在线上下文，并增加服务端滚动摘要、用户偏好和任务记忆的明确数据模型。
- **[不进入关键路径]** 不让 SD 卡参与实时 ASR → DeepSeek → TTS；不开发通用远程文件管理，也不让 Agent 任意浏览 SD。
- **[待明确]** 当前固定 `session_id` 如何映射到设备、用户和长期会话。

#### V1 后续

- 把设备侧记录升级为 JSONL，并实现方案 A 的增量上传、幂等去重、ACK 和断网补传；
- 服务端可按明确用途生成每日摘要、长期记忆、用户偏好和任务整理结果；
- 通过受限的下行同步把 `summary.json`、`memory.json` 等副本写回 SD，使用版本号和校验和，不直接覆盖未知文件；
- 增加文件轮转、SD 错误恢复、拔卡处理和隐私清除机制。

#### V2

- 评估方案 C，建立双向 WebSocket 设备协议；
- 支持受限的远程存储读取、资源更新、日志获取和设备控制；
- 根据真实维护需求再决定是否增加网页文件管理；若只需导出归档，不建设通用文件后台。

### 14.7 与 HoloCubic 的区别

HoloCubic 中的 TF 卡主要用于图片、视频、天气图标等媒体和资源文件，也可配合网页文件管理功能使用。AmbientDesk 可以借鉴“资源放在可更换存储中”和“提供受限管理入口”的思路，但不应直接照搬为语音上下文架构。

AmbientDesk 的语音对话依赖服务端 ASR、DeepSeek、TTS 和未来 Agent 编排，在线每轮数据天然先经过服务端。因此服务端数据库更适合作为上下文中心，SD 卡更适合作为设备侧辅助存储。两类项目的核心数据流不同，不能因为都使用 TF/SD 卡，就让 Agent 以远程文件浏览代替会话数据库。

### 14.8 仍需产品与架构决策

以下问题不会阻塞当前 V1 对话，但在开发同步前需要用户确认：

1. **身份模型**：`ambient-desk-01` 是设备 ID、用户 ID 还是长期会话 ID；多设备和多人使用时如何隔离。
2. **离线范围**：断网时只记录诊断/待办，还是需要离线语音识别和本地指令；后者会显著扩大 V1 范围。
3. **上行数据范围**：只上传设备离线产生的数据，还是也用 SD 记录对服务端 SQLite 做对账；推荐前者为主、后者只做修复工具。
4. **下行记忆范围**：只同步摘要和偏好，还是同步完整历史；推荐只同步体积小、用途明确、可版本化的派生数据。
5. **隐私与保留**：SD 对话是否明文、是否需要加密、最大保留周期、用户如何一键清除和导出。
6. **V2 通道**：出现持续双向设备控制需求后采用 WebSocket，还是继续使用多个窄 HTTP 接口；当前无需提前决定。
7. **事实源演进**：若未来采用 DeepSeek Harness 或其他 Agent 事件存储，是继续以 SQLite 为主并做适配，还是执行一次明确迁移；不得长期双写成两个事实源。

最终建议不变：**当前以服务端 SQLite 保存在线上下文，SD 卡保存本地归档和未来断网队列，双方只通过用途明确、可认证、可幂等的增量同步协议交换必要数据。**
