# VoxConductor 设备端语音与记忆实施方案

更新日期：2026-10-10。本文描述当前开发版；本次仅发布文档与素材，最新固件代码另行整理。

我把设备端的职责拆成轮次、存储、上下文、工具、音频和桌面模块。基础唤醒、查询和设备控制已有实机演示；唤醒词打断已出现成功记录，但播报连续性、回声和多轮边界仍在联调。游戏已备份并移除。本次文档更新不执行 C 构建或烧录。

本文统一维护语音对话功能的职责、实现、限制与验证步骤。连接和启动说明见 [设备直连](DEVICE_CLOUD_VOICE.md)。固件已迁移至定制PCB引脚，见 [硬件与接线](HARDWARE_V1.md)；旧原型的验证结果不代替新板实测。

## 目标与流程

ESP32-S3 负责采集、播放、轮次管理、模型调用、上下文与 SD 记忆、工具执行和确认。ASR、DeepSeek、TTS 推理仍在云端，需要互联网，不属于本地大模型或离线语音。

优先在设备端形成闭环；大量历史检索、批量整理、跨设备同步以后按实际负载迁至桌面服务，不预设迁回整条链路。SD 增加持久容量，不增加 MCU 算力、TLS 内部堆或实时音频处理能力。

一次对话：开始采集并上传 → 最终转写归档 → 处理本地命令或组装上下文 → 按需选择工具（工具阶段静默）→ 接收完整最终回答并释放 LLM 连接 → 再启动 TTS → 等待播放结束并保存状态与上下文。空闲时处理提醒和摘要。各模块按问题需要参与，不强制每轮执行全部功能。

当前继续使用 DeepSeek，普通对话与后台摘要均设置 `thinking.type=disabled`。简短、解释、详细回答的输出上限分别为 180、400、1600 Token；工具开放时至少保留 400 Token，供参数与协议消息使用。后台摘要同时整理讨论状态，输出上限为 1400 Token。以上是请求上限，不是每次固定消耗，也不是中等推理强度。不推进模型更换或 GPT-Live 接入。

## M0：轮次管理与日志

作用：关联录音、识别、生成、播放和归档，并明确各阶段状态。

`app_turn.*` 使用启动随机标识和轮次序号，独立维护各阶段状态，允许输入与识别重叠；当前不让 LLM 与 TTS 连接重叠。失败或取消后拒绝迟到的成功事件。`app_turn_log.c` 默认按轮次输出开始、聆听、识别、生成、播放与终态摘要，详细资源与协议诊断按需开启。首次 I2S 提交不是扬声器实际首声；“请求成功”也不能证明听感连续。动作状态周期日志保持关闭。

## M1：SD 记录与恢复

作用：为会话恢复、摘要、长期记忆与检索保存持久数据。

`app_history_store.*` 追加 `dialogue.jsonl`，交替写入两份带校验值的快照并读回检查；`app_storage.*` 管理 SD 可用性，不因挂载失败自动格式化。启动只读有上限的快照，不加载全部日志，不重播或执行旧对话。

原文、生成状态、PCM 提交和终态分别记录。“生成了”不表示“用户听到了”。长回答在日志中按完整 UTF-8 字符分块，每块最多 2047 字节，并记录 `text_offset` 和 `text_total_bytes`；保留完整生成原文不意味着近期窗口也保留全文。

当前卷上限 8 MiB；在新一轮用户原文开始前、剩余不足 128 KiB 时，封存到空闲的 `dialogue.1.jsonl`～`dialogue.4.jsonl` 槽并重建当前卷索引。最多保留四份封存卷，不覆盖或自动删除旧记录；封存槽满或轮转失败时停止该轮日志追加，快照仍独立更新。定向删除遍历当前卷与四份封存卷，全量清空也包含这些卷。旧文本不自动导入。

`tools/backup_sd.py` 在电脑上复制固定文件白名单，核对 SHA-256 并写入清单，默认不修改原卡。只有显式 `--retire-archives` 才在核对后删除原卡的封存卷，保留当前卷与快照；`erase.pending` 存在时拒绝此清理。先给设备断电再取卡，不能让电脑与 ESP32 同时写同一文件系统。使用方法见 [设备直连说明](DEVICE_CLOUD_VOICE.md)。

## M2a：上下文预算与增量摘要

作用：最近保留原文，较早内容保留要点，控制每次输入与内存使用。

- 最多 6 对近期问答，先计入当前问题、摘要、相关记忆和讨论状态，再按 12 KiB 正文字节预算选择最新完整问答；模型请求 JSON 上限 32 KiB。用户输入与近期窗口单条文本上限 2047 UTF-8 字节；单轮生成可达到 16383 字节，进入近期窗口时超过上限的长答案带明确摘录标记，不伪装成全文。真实 token 取供应商 usage，不以字节数冒充。
- 淘汰一轮时生成有界本地摘录，并积累待整理原文。待整理内容达到 2048 字节、对话空闲至少 30 秒且内部堆余量足够时，设备发起后台 DeepSeek 摘要请求。
- 摘要输入为旧摘要、待整理原文、当前讨论状态和有限近期材料；旧历史摘要与活动讨论分别整理，近期材料只用于更新讨论，不重复写入旧摘要。作业只操作独立副本；结果提交前核对版本、待整理内容与讨论状态，SD 保存成功才推进。
- 新会话、删除或新的淘汰会使旧结果失效。新录音先开始，ASR 连接等待被中止的摘要网络调用退出，避免两个语音侧 TLS 会话叠加。
- 摘要失败最早 60 秒再试；待整理缓存 12 KiB 封顶。满后不继续增长，新淘汰信息仍进入本地摘录和原文日志。摘要不保证覆盖全部历史细节，M5 用于找回原文。

摘要是可能有误的压缩材料，不是事实数据库；当前用户的明确纠正优先。阻塞网络调用仍受超时约束，不承诺后台作业零影响。

## M2b：长期记忆

作用：把明确偏好和事实从近期窗口分离，处理更新、过期与删除。

用户明确说“记住/修改记忆”后，模型可调用 `prepare_memory`；设备校验名称、内容和有效期，等待下一轮“确认保存”，120 秒有效。SD 写入成功才确认保存。同名替换并递增版本，保留来源轮次和更新时间。

单个本地档案最多 16 条，不识别说话人。临时条目到期不进入上下文；“今天”最多保留至北京时间当日结束。“开始新对话”保留长期记忆和任务。

每轮先选择通用沟通偏好，再选择与当前问题或短追问主题相关的记忆，最多注入 6 条，不把全部 16 条固定发送给模型。相关性采用有限分类、英文实体和相邻中文字符匹配，不是向量检索。饮品偏好、回答偏好等有限别名可合并；条目保留稳定 ID、来源轮次、分类、原始名称与最多 8 次旧版本的来源/名称/值。

“删除记忆：名称”经确认后删除该条目，移除来源或名称/值/别名命中的关联对话轮次，保留无关记忆、任务与原文；摘要、待摘要材料和活动讨论重新整理，不继续使用旧聚合内容。删除通过临时原文文件替换和恢复屏障推进，失败不报告成功；修复 SD 后可说“重试删除”。匹配范围包括已保留的旧版本，但不保证识别任意语义改写。“清空全部记忆”仍是单独确认的全量操作。旧 `conversations.txt` 与已导出的副本需单独管理。

## M2c 活动讨论状态

作用：让“第二个方案”“继续讲”“不要依赖电脑”等短追问延续同一目标与约束，而不是只依赖最近一句回答。

`app_conversation.*` 保存一个最多 3 KiB 的活动讨论，包含目标、约束、未解决问题、最多 3 个候选方案、已选择编号、来源轮次和版本。比较问题可建立新讨论；明确的编号选择与约束修改更新当前状态。解释步骤的编号不直接替换候选方案，用户未选择时不替其作决定。只在短追问或与目标相关的问题中注入该状态。

本地规则先更新，空闲摘要作业再提交结构化整理结果；字段、长度、选项数与选择编号需校验，旧版本不能覆盖新的纠正。开始新对话或删除相关来源会重置讨论状态。它是有限的对话材料，不是任意任务规划器，“选择方案”不等于授权执行设备动作。

## M3：设备工具与 Agent Loop

作用：需要实时信息时读取设备数据，需要动作时以实际执行结果为准。这是设备内的原生函数调用循环，不是通用 MCP Server。

当前把经过筛选的白名单工具提供给模型，以 `tool_choice: auto` 决定是否调用，不再主要靠问题中是否包含某几个能力词开放工具。时间、天气、任务、记忆、历史、本机状态与设置、受限局域网设备分别有参数约束；设备仍负责类型、长度、权限、重复动作和返回值校验。明确的本机音量、主页与退出等快捷命令可在 ASR 后本地处理。

一轮最多 3 次模型请求、2 批工具往返、合计 4 次工具调用。工具旁白不送 TTS；所有工具处理完成并收到合法的最终回答后才开始播报。没有通用脚本执行、任意 URL 或任意 SD 文件访问。已经完成的写操作不会因为后续 TTS 失败而回滚，因此操作成功与播报成功必须分开报告。

天气工具读取设备配置城市的缓存，`detail` 支持 `current / uv / air / wind / hourly`，包含当前天气、UV 数值及当日超过 3 的时段、USAQI/PM2.5、风和未来 12 小时预报。数据带来源、时间与有效性，不支持任意城市查询；过期或缺失不能用旧聊天内容补造。

音量、主页等动作要检查执行后的实际值和持久化结果。“请求被接受”不是“已经应用”，助手说“完成了”也不是证明。长记忆、任务变更和外设写操作继续按各自规则准备/确认，不能由一句笼统的确认扩大操作范围。

## M4：语音收发、播放与取消

我把低延迟和资源稳定分开处理：ASR 仍在录音过程中增量上传；LLM 完成工具调用和最终回答后释放连接，再建立 TTS 会话。这样会放弃“模型边生成边播”的部分首声收益，但能降低多条 TLS 链路同时占用内部 RAM 的峰值。

`app_cloud_asr.c` 上传 16 kHz PCM，长按录音松开发送，最长 20 秒；只有最终转写进入后续流程。`app_sse.*` 负责组合文本和工具参数，检查长度、结束原因与流完整性。旧 `app_speech.*` 并非当前默认构建路径，不能再用它解释当前播放时序。

`app_cloud_tts.c` 用单个 WSS 会话合成一个最终回答，PCM 队列位于 PSRAM，容量 384 KiB，普通回答起播预缓冲 24 KiB（24 kHz、16 位、单声道约 0.51 秒）。接收和消费解耦；队列耗尽的补缓冲与硬件 DMA 供给间隙分别观察。

10 月 10 日的最新调整把扬声器 DMA 从 4×160 帧改为 8×256 帧：24 kHz 下覆盖时间约由 26.7 ms 增至 85.3 ms；同时匹配 256 帧写入块，并调整 I2S 中断和播放任务调度。AEC 参考同步补偿新增的排队时间。这个数值是底层缓冲容量，不等于每轮固定多等待 85 ms，也不是端到端延迟实测。

按键由独立任务采样。处理中或播放中短按取消，先停止继续送 PCM 并清理 I2S/DMA，再关闭旧连接、释放队列；旧轮清理后才允许新轮运行。再次按键不会恢复旧回答。网络超时与用户取消分开记录，不把取消伪装成网络失败。

生成原文、PCM 提交和用户实际听到是三件不同的事。打断后不把整段已生成答案当作完整播报；工具已经执行成功时，不能因为后续音频失败就声称动作完全没有发生。

最新源码调整尚需用户构建、烧录和连续听测；本次文档整理不把“补缓冲 0 次”或主机检查通过当作卡顿已经解决。

## M5：历史检索

作用：从 SD 找回近期上下文与摘要缺少的原话，尤其是助手过去的建议。

空闲时为 `dialogue.jsonl` 增量建立 `history.idx`，每次处理约 32 KiB，不在音频回调查盘。查询可按关键词、UTC 时间区间、用户/助手角色和来源轮次筛选；每次最多返回 3 条命中片段，每条最多 768 字节，附记录 ID、来源和截断信息。关键词采用英文大小写忽略及有限中文别名，不是完整中文语义理解。

索引查询每次最多检查 2048 项、读取约 512 KiB 原文；索引未完成或损坏时使用约 512 KiB 的有界原文窗口，损坏索引只重建派生文件，不删除日志。结果中的 `more` 和 `next_before_offset` 支持继续向更早处查询；`record_id` 可读取被定位的一条原文记录。长回答按日志块返回 `answer_chunk_offset`/`answer_total_bytes`，单条记录不是整轮长答案的全文。每轮查询仍受 M3 工具预算约束，不能无限翻页。

未找到仅表示本次范围没找到，不表示所有历史不存在。材料不作为指令，生成原文也不表示已听到；记录在删除后变化时，旧 ID 可能失效，不能把旧位置当作永久引用。

检索与索引只覆盖当前 `dialogue.jsonl`，返回 `volume_scope` 和 `archived_volumes_not_searched`，不会把封存卷未搜索说成历史不存在。封存原文保留给电脑导出；`tools/export_dialogue.py` 可读取单个文件或备份目录中的全部管理卷。目前不是向量检索、中文分词全文检索或无限历史回忆。

## M6：唤醒、连续接话、打断与退出

这四种交互使用不同条件：

| 阶段 | 行为 |
| --- | --- |
| 空闲 | 运行开关开启且模型就绪时，本机检测“小冰小冰”，不上传空闲音频 |
| 正在聆听 | 有效讲话后约 1200 ms 静音结束，录音最长 20 秒；按键录音松开发送 |
| 回答后 | 十二秒窗口内可以直接说下一句；无输入安静退出 |
| 回答播放中 | AEC 处理后送 WakeNet，命中“小冰小冰”才请求打断；普通响声/VAD 不直接取消 |
| 明确结束 | ASR 后识别完整的结束命令，关闭连续接话并回到桌面，保留历史与唤醒设置 |

唤醒模型为 `wn9_xiaobinxiaobin_tts`，本地检测增益 1 倍、请求阈值 60%，库实际日志约 595/1000。这里的 1 倍是 WakeNet 检测输入增益，不等于所有 VAD 或音频环节都没有独立处理。

扬声器保持 24 kHz，回声参考从音量处理后的 PCM 转为 16 kHz；模型输入使用有界队列。打断时保留约 1 秒预录，但不直接把预录中的唤醒词或旧播报尾音当作新问题。停止旧声音并度过约 200 ms 尾音保护后，还需新的有效人声证据；只有唤醒词、随后保持安静时，不应上传旧回答再请求模型。

“结束对话”“退出语音”“不聊了”等完整命令在本地处理，允许限定的礼貌修饰或前置唤醒词，不对任意含有这些字的长句做子串匹配。“不要结束对话”不能退出，“谢谢”也不默认退出。回答中可以先用唤醒词打断，进入聆听后再说结束命令；不是在播放中常驻识别所有结束短语。

旧轮退出前不创建第二条云端流水线；按键取消优先，并清除待接话。声学接续仍受箱体、距离、回声、失真和任务调度影响。目前有成功打断日志，不等于完成稳定全双工验收。

## M7：本机任务与局域网设备

作用：把对话请求变为真实保存、可查询状态的提醒、待办和设备操作。

任务表最多保留 8 条记录，包含提醒/闹钟、待办与备忘录；满时先清理终态记录，不移除待处理任务。提醒创建需要有效时钟与持久保存成功，无需再次说“确认执行”；待办创建、完成及已有任务的语音修改仍需确认。每条任务有稳定 ID，同名任务不按第一条猜测目标：模型先读 `get_tasks`，再用 ID 准备修改；同名待办的旧标题完成命令会要求选择具体条目。

`prepare_task_change` 支持编辑标题/钟点/循环规则、稍后提醒、完成、取消、删除。设备保存待确认 ID 和参数，120 秒内下一轮“确认执行”才落盘；不确认、过期或写入失败不改变原任务。钟点修改同样由设备计算 UTC，不接受模型把钟点猜成 60 秒。图形任务页可选择条目、确认“稍后五分钟/完成并结束任务/取消/删除”，SD 操作排到语音互斥的后台执行，不在 LVGL 帧回调查盘。

明确提醒/闹钟与新增备忘录按规则强制使用任务工具，保存前不播放模型声称成功的文字。备忘录 kind=note，保留原话连续片段，最多四十个中文字符，不带到期/循环，不自动播报；明确新增直接保存，无需再次确认。待办创建与已有任务修改仍保留确认。实际持久保存成功才回复，失败不报告已设置。

时间支持 60 秒至 30 天的相对倒计时，以及北京时间的指定钟点（未指定日期、今天、明天、后天）。模型提取 `hour/minute/period/day`，ESP32 计算到期时间。未指定日期和上午下午的 1～12 点选择最近未来的上午或下午时刻，可跨日；指定日期时只在该日选择。单次提醒明确早晚或 24 小时制但未给日期时按今天计算，已过则拒绝。钟点提醒允许少于 60 秒，不默认替换为一分钟。

循环规则为 `daily`、`weekdays`（周一至周五，没有节假日表）和 `weekly`，仅用户明确要求循环时创建；循环钟点今天已过则从下一适用日期开始。每周规则可指定“每周一”至“每周日/天”（也接受“每星期一”等）；未指定星期时以首次日期为锚点。先确定可用日期，再在该日选择最近未来的上午/下午，不能把周末的下午误挪到周一下午而跳过周一早上。下次到期沿原钟点/星期计算，跳过错过的周期，不以播报完成时间累计偏移。“稍后五分钟”只推迟这次，保留以后循环的原锚点；编辑钟点/循环规则更新锚点，标题编辑不改锚点。明确把终态任务修改为循环时重新设为待处理。没有任意日期、法定节假日或账号日历能力。

到期且语音空闲时，先持久化提醒提交状态及循环任务的下次到期，再显示“提醒中”。联网且云端可用时 TTS 直接播报“时间到了，提醒你：事项”；断网、未配置云端或云端播放失败时播放固件内置语音“时间到了，请查看屏幕上的提醒。”，具体标题显示在屏幕。无前置提示音，不调用 LLM。忙时等空闲，晚到超过 5 分钟记录错过；播放结果保存为已播报、取消或失败，循环任务继续保持下次待处理。正常复位不重复提交已处理周期。PCM 提交成功仍不代表已确认扬声器出声。

本地任务与快照在检查云端密钥前初始化，所以云端配置失败不关闭任务列表、专注与本地提醒。钟点提醒仍要求有效时间；断电冷启动未校时不能承诺准时提醒。专注计时采用单调时钟，不依赖 SNTP。

2026-10-02 开始接入提醒连续性修复；播报期间临时提高任务优先级，完成、失败或取消后恢复，具体值以当前播放实现为准。短提醒尽量等音频接收完成再起播；长提醒在队列接近容量时起播，正常容量下阈值为 320 KiB，并保留最大解码块的空间，避免满队列等待完成事件。提醒首声可能稍晚，普通回答仍使用 24 KiB 预缓冲。新增“提醒起播”的完整接收/缓冲/优先级字段，以及“提醒语音”的缓冲等待次数和时长。

提醒文字中的方框已确认涉及字体缺字。`app_ui_font_14.c` 已补齐“醒”、中文冒号及常见提醒用字/标点，保留原显示内容。常见文字的字体覆盖检查已通过；字体仍是子集，不保证任意生僻字均可显示。修复后的声音连续性与屏幕显示均待实机确认。

局域网工具只访问最多 4 个编译期配置目标，使用共享令牌。查询 `GET /state`，确认后 `POST /command`，携带稳定命令 ID 与布尔 SET 状态，不使用 toggle。发送前保存意图；回执核对 ID 和状态，超时视为结果未知，不自动重试或重启重放。

`examples/lan_switch` 提供另一块 ESP32 可运行的低压 LED 开关程序，保存最后一个命令 ID，相同 ID/参数不重复切换，参数冲突拒绝。这不是无限历史去重、物理负载检测或安全关键控制协议。HTTP 示例仅用于可信局域网，不能用于门锁、加热器等负载。食材清单等结构化能力以后增加独立只读协议。

## M8：桌面工具与专注

作用：把语音创建的任务变为可看、可操作的本机界面，让日常计时与短时娱乐无需模型参与。

app_ui.c 的四个基础页为时钟、天气、语音与桌面工具。当前姿态切页、单击进入/确认、双击返回；二级工具为三列九宫格。时钟直接进入闹钟，待办/备忘录留在任务入口。天气与闹钟支持倾斜幅度变速，主页可为圆形时钟或壁纸+数字，屏保固定无壁纸圆形时钟。

`app_focus.*` 负责单调时钟倒计时：1/5/15 分钟，番茄钟默认 25/5 分钟，工作时长可选 15/25/45，休息可选 5/10。阶段到期只发出一次通知，下一阶段等待手动继续；完成次数独立累计。暂停不计时，SNTP 校正不使剩余时间跳变。NVS 保存剩余值，重启后显示中断并保持暂停，不自动把断电时间当作已计时。明确语音命令“开始专注/开始番茄钟/暂停专注/继续专注/停止专注”在 ASR 后本地执行，不发给 LLM。

游戏相关内容已在 10 月 8 日的收敛调整中备份并移除，不占当前固件的功能入口和构建范围。

app_media.* 管理 SD 音乐、环境音、壁纸和同网网页；媒体实际 WAV 为 24 kHz/16 位/单声道，浏览器转换不是原生 MP3/FLAC 解码。网页状态/设置/任务/历史复用同一设备数据，非第二套数据库；改版设计见 [网页管理](WEB_MANAGEMENT_DESIGN.md)。

音量默认 35%、基础亮度 100%；设置与专注状态由后台存 NVS，失败明确暂时生效。详细输入、规则与验收见 [桌面说明](DESKTOP_TOOLS_AND_GAMES.md)。

## 功能验证

以下步骤用于实机验证，未执行的项目不视为已通过。主机测试不能代替设备编译链接、云端联调和声学测试。

### 1. 编译前

1. 备份 SD 上已有对话，尤其是后面要测试删除时。不要带电拔插 SD。
2. VS Code 的 ESP-IDF 项目路径指向 `voxconductor/firmware`，不是仓库根目录。
3. 核对私有 Wi-Fi、百炼、DeepSeek 配置。ASR 现在使用实时模型 `qwen3-asr-flash-realtime`，不是此前整段 ASR 模型；检查该模型在密钥所属地域可调用。
4. 执行重新配置、编译、烧录。新增 ESP-SR 2.5.4 会由组件管理器下载，首次时间可能较长。不要同时点击多个构建任务。
5. 核对小冰小冰模型、运行开关和模型分区。隔离问题时先回归按键路径；恢复声学功能后单独测试。完整烧录模型分区，不能只烧应用。

### 2. 正常语音、日志、流式输出

关闭电脑 FastAPI，但保留互联网。长按说“请用两句话介绍一下杭州”，松开发送。

检查：聆听→处理→播放；串口有同一轮次的用户、助手、终态。识别全程包含录音，另有“松开后识别等待”；首文本、首 PCM 与首次 I2S 均有值。回答按句播放，没有重复、乱序或长时间断音。日志里的“回答流水线”不是纯 LLM 延迟，不与旧非流式数字直接相减。

连续做 10～20 轮，观察内部堆、最大连续块和任务栈余量是否持续下降。有重启、看门狗、分配失败或音频断续时保留整轮日志，不只截最后一行。

当前 Agent 与播放改动重点回归：

- 问“介绍一下杭州”“为什么天空是蓝色的”：应记录“Agent路由：直接回答”，模型请求1次、工具调用0次，无“先查缓存/缓存没有”的中间播报。先问天气再问常识，也不能继承天气工具。
- 刚说过自己的偏好，再问“我喜欢什么饮品”：从近期上下文回答，不查历史。问“查一下之前关于咖啡的原话”：才开放search_history；未命中不编造原话，不先播报查询过程。
- 问天气：工具轮旁白静默，通常1次工具调用、2次模型请求，再播放最终答案。仍需确认过期、不可用和城市不支持时如实回答。
- 分别要求“一句话”“解释原因”“详细说明具体步骤”：检查回答长度随需求变化。详细回答可超过旧的 2047 字节生成限制，近期快照中的长回答应带摘录标记，SD 原文块应保留总长度与偏移，不截断中文字符。
- 请求稍长的回答：检查“最终文本接收完成”早于整轮结束，普通最终回答的 TTS 会话数应为 1、文本追加段数可大于 1；听感无重复/乱序。观察缓冲等待次数/时长与内存变化，不能只凭会话数判断声音已经连续。
- 在首句播放、后续句排队及网络等待时分别短按取消，再立即发起新问题；旧句不能续播、串入或变调。播放中断网后也应释放旧队列并允许下一轮。

### 3. SD 恢复与近期对话

说“我家的猫叫糯米”，等待播报与快照保存。复位，再问“我家的猫叫什么”。然后说“改一下，现在叫汤圆”，完整结束后再复位询问。

应恢复最新保存的有限上下文，不自动重播旧回答。不插卡启动时普通联网对话仍可运行，但需要持久确认的记忆与任务不能报告已保存。

### 4. 长期记忆、更新、过期和新会话

1. “记住我的饮品偏好是茶。”等待助手复述名称和值。
2. “确认保存。”应明确保存成功。
3. “查看记忆。”核对真实条目名称和值。
4. “开始新对话。”再问饮品偏好，应使用长期记忆而不是近期窗口。
5. “修改记忆，饮品偏好改成咖啡。”→“确认保存”→复位→查看记忆，应只有同名新值。
6. “暂时记住，我今天在杭州。”确认后检查条目带有效期；过期后不再进入上下文。“今天”以北京时间当日结束为上限。
7. 准备一条记忆但不确认，等待超过 120 秒，再说“确认保存”，应提示没有有效待保存项。

模型可能选择不同名称，同名更新和删除必须以实际保存名称为准，不凭示例猜测名称。

增加相关性回归：分别保存饮品偏好、回答偏好与无关事实，再问“如何给设备供电”。通用回答偏好可参与，不应每轮带入全部无关条目；已过期记忆不应参与。用“饮料偏好”和“饮品偏好”更新同一值后查看记忆，不应产生这组已定义别名的重复条目。其他任意近义表达不保证自动合并。

讨论状态回归：先问“比较两种不依赖电脑的供电方案”，再问“详细讲第二个”，随后说“现在可以依赖电脑，但不要改电路板”。检查编号和当前目标能够延续，新约束替换被明确纠正的旧限制，未被纠正的限制仍保留。再说“开始新对话”，旧讨论不能继续当作当前目标；方案选择不能触发未确认的设备操作。后台结构化整理后也不能把解释步骤误识别为新方案。

### 5. 滚动摘要与旧原文

连续对话超过 6 轮，内容需要足够长，让被淘汰的原文累计达到 2048 字节。空闲至少 30 秒，查看“摘要作业版本”“滚动摘要已保存”；内部堆不足时不会启动摘要，短对话也可能尚未达到阈值。

问早先谈过的偏好、修改或未完成问题；摘要可能保留要点但不保证逐字复述。问“查一下之前关于咖啡的原话”，应看到 `search_history` 工具调用，返回有限范围的原文，不应凭空编造。

从 SD 日志中选取已存在的样本，验证时间区间、角色与来源轮次筛选；结果有 `more` 时，使用 `next_before_offset` 查更早记录，再用 `record_id` 读取所选原文块。长回答的原文块应具有 `answer_chunk_offset`/`answer_total_bytes`，不能把单块称为整轮全文。一次对话可能受工具预算限制而不能读完所有分页，未命中不能被解释为历史一定不存在。索引构建、损坏重建等存储场景先在备份副本上测试，不在唯一原卡上破坏文件。

在摘要进行时开始录音，检查录音仍启动，旧摘要作业不覆盖新的会话或删除结果。网络调用退出可能需要等待其超时，不能用此项判断毫秒级打断效果。

### 6. 时间与天气工具

问“现在几点”“杭州现在多少度，体感多少”。串口应显示 `get_time` / `get_weather` 工具；天气应与当前缓存一致并说明城市。问“明天北京天气”应说明当前工具范围，而不是将杭州当前数据作为北京预报。

工具响应过期或获取不到时不能编造。每轮最多两次工具往返、合计四次调用；查看日志没有无限循环。

回归测试“杭州今天天气怎么样”：即使模型先生成查询旁白再返回get_weather调用，旁白也不能播放。日志应出现“工具旁白已屏蔽”“设备工具完成：get_weather”，随后得到基于工具数据的最终回答。普通聊天也在完整生成后进入 TTS 播放，提醒仍在工具保存完成后才播报。若失败，保留“LLM流在DONE前结束”“LLM SSE校验失败”或“工具消息不完整”及同轮最终错误日志，以区分断流、结束原因和参数异常。

### 7. 按键取消与上下文

启动应出现“按键独立任务已启用：GPIO16，10ms采样，500ms长按”。按键检测不再依赖LVGL定时器。按下/松开电平与长短按事件的临时诊断日志已移除，检测逻辑保持不变。播放时轻按100～200ms并松开，应触发下述取消日志；不要以没有电平或事件日志判断按键未被检测。

请助手给两句建议，第一句播放时短按。应终止回答而不是暂停：停止并清空I2S DMA、关闭旧TTS连接、释放队列，记录取消并回到空闲。串口应出现“按键终止当前对话”“终止播放并清空DMA”及“当前回答已终止”。清理期间再次短按不能恢复；回到空闲后单击按所在页面进入/确认，不能续播旧回答；切页用姿态。随后长按发起新问题，检查没有旧音频或变调。连续重复至少五次，并测试一句话末尾与下一句开始之间取消。

下一轮问“刚才你说到哪里”。连续 TTS 没有可靠的逐字播放位置，回答中断后不能把已发送的文本说成你已听到；应保留用户问题和中断状态。识别和网络等待期间也短按取消，随后应能重新长按开始，不白屏、不重启、不残留旧音频。

### 8. 提醒与待办

说“一分钟后提醒我喝水”，无需再说“确认执行”。串口必须出现“提醒工具结果：status=saved，到期UTC=…”，设备才会播报已设置。倒计时从任务保存时开始，不从确认语音结束时开始。可说“查看提醒”核对待处理记录。到期应显示“提醒中”，联网直接播报事项，无前置提示音；短按可取消。已校时后断网，应听到本地“时间到了，请查看屏幕上的提醒。”且屏幕显示喝水。正在语音对话时等空闲再提醒，超过到期 5 分钟记录错过。复位不会重新创建已经提交过的周期。

本次修复回归：连续创建三次一分钟喝水提醒，检查到期后的整句是否连贯，“提醒中”及“时间到了，提醒你：喝水。”是否还有方框。短提醒起播日志应核对完整接收与实际任务优先级，结束日志应显示缓冲等待次数/时长；首声允许有收齐音频的等待，不把它与中途卡顿混为一项。播报时短按，应停止而非暂停；随后发起普通问题，旧提醒不能续播。日志中等待为零仍不能单独证明 I2S 或扬声器无卡顿。

“提醒我”类明确请求强制走提醒工具，并在工具执行前不播放模型文本；成功回复来自本机保存结果。未正确返回工具时应报错，不得仅凭模型文字声称已设置。SD写失败时应显示not_saved且任务表不增加。其他措辞仍由模型选择工具。

时间支持60秒至30天的相对倒计时，以及北京时间的钟点提醒（未指定日期、今天、明天、后天）。钟点由模型提取hour/minute/period/day，ESP32计算到期UTC，不由模型换算秒数。未注明上午下午的1至12点选择最近未来的上午/下午时刻，允许跨日；明确指定日期时只在该日选择。明确早晚或24小时制、未给日期时按今天计算，已过则拒绝并要求说明新日期。钟点提醒可少于60秒，不强行补足一分钟。

验证：16:59说“五点零二分提醒我喝水”应回报当天17:02；17:03说同句应回报次日05:02。说单次“今天下午五点零二分”而该时间已过，应说明未设置，不自动改为明天。说“明天上午五点零二分”应回报明日05:02。日志到期UTC应与播报一致。测试过程中以实际设备校准后的时间为准，不据此推断完整日历能力。

普通确认回答和提醒语音均打印“TTS PCM幅度(音量缩放前)”：峰值为零表示读取到的 PCM 全为零；非零幅度和 I2S 提交成功仍不等于实际出声。若仍无声，请保留幅度、采样数、提醒语音结果和 I2S 错误日志，并说明普通回答和到期提醒语音是否分别可听见。

“添加待办买牛奶”→“确认执行”→“查看待办”；再说“完成待办买牛奶”→“确认执行”，状态应改变。未确认、确认超时或 SD 写失败不能报告创建成功。同名待办应要求指定目标，不自动完成第一条。

创建“每天上午九点提醒我喝水”“工作日下午三点提醒我站起来”“每周一上午十点提醒我开会”，在任务详情核对首次日期与循环标签。到期后核对下次时间仍为原钟点；五分钟稍后不改变循环锚点。用“修改喝水提醒为下午四点”准备修改，先不确认，原任务应不变；再准备并“确认执行”后核对新日期/钟点。任务图形操作、完成/取消/删除与 SD 写失败的测试见 [桌面交互与工具](DESKTOP_TOOLS_AND_GAMES.md)。跨天/周末跳过等计算也有 C 回归用例，尚未执行。

### 9. 删除与不再引用

先备份，再测试。先记录一条要删除的偏好和一条无关事实，再用“删除记忆：实际名称”准备定向删除，说“确认清空”才执行。复位后，删除条目及命中的关联原文不能通过近期窗口、摘要或历史检索恢复，无关记忆、任务和原文应保留。更新同名记忆再删除时，已保留旧版本的名称、值与来源也应参与清理。语义改写但没有来源/名称/值命中的材料不保证被识别。

“清空全部记忆”→“确认清空”才清理当前卷、四份封存卷、快照中的对话/记忆/任务及派生索引。旧 `conversations.txt`、电脑上的导出副本不在范围内。中途存储失败时不能显示删除成功；`erase.pending` 存在时禁止恢复/检索旧数据。定向删除同样遍历封存卷，可在修复 SD 后说“重试删除”，不自动扩大成全部清空；损坏原文无法安全改写时仍提示未完成。全量清空仍需单独重新确认。

### 10. 小冰小冰、连续接话、打断与退出

保持摆位、音量、固件和测试句一致，以下是回归步骤，不表示全部通过：

1. 空闲唤醒十次，记录成功次数；回答后直接追问，核对十二秒窗口。
2. 连续播放长回答，完全不说话；检查是否自我打断，听测是否卡顿。
3. 在首句和后续句说“小冰小冰”，看到聆听后提出一个不同的新问题；核对检测、停止旧音频、识别新问题三段日志。
4. 只说唤醒词，随后保持安静：不能把旧回答尾音识别成新问题并自动回答。
5. 聆听时说“结束对话”：返回桌面，不继续十二秒接话；说“不要结束对话”不应退出。
6. 处理或播放时按键取消：清理后不续播、不自动接话；下一次仍能重新唤醒。
7. 重复多轮，记录内部堆/最大块与播放诊断；不把单次命中或零补缓冲当作稳定结论。

音乐和本地提醒不承诺同一唤醒词打断路径。诊断录音只在明确启动诊断后采集，不随 GitHub 文档发布。

### 11. 第二块 ESP32

按 [局域网设备接入](LAN_DEVICE_PROTOCOL.md) 配置示例和白名单。先查状态，再准备打开 LED；不确认时不能改变输出。确认后应改变，重复“确认执行”不能再次发送同一待确认操作。

测试错误令牌、离线目标与超时。不能报告执行成功或自动重试；先查询实际状态。示例只用于低压 LED，不接安全关键负载。
