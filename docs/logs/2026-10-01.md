# 2026-10-01｜连续 TTS、讨论状态与历史记忆优化

## 今日目标

先改善长回答连贯性，再完善有界 Agent、追问承接与历史记忆。

## 已完成

- 最终回答复用一个 WSS TTS 会话，持续追加文本，输入结束只发送一次 finish。
- 文本发送与 PCM 消费分离，启用 WebSocket 独立发送锁，处理“回调等待队列空间、播放任务等待同一锁”的互相等待风险。
- 使用 4 KiB 可复用文本环形队列、384 KiB PCM 队列和 24 KiB 预缓冲；生成文本上限为 16383 UTF-8 字节，归档按字符边界分块。
- 简短、解释、详细回答使用 180/400/1600 Token 上限；近期窗口保留最多六对问答和约 12 KiB 正文预算。
- 通用偏好优先，其次选择当前问题相关的长期记忆；不每轮注入全部条目。
- 活动讨论保存目标、约束、候选方案与选择；避免把解释步骤编号覆盖成新候选，纠正约束时替换对应旧限制。
- 工具阶段静默、同参重复查询受限；允许有限换词检索，但不继承写权限。
- 增加历史筛选、分页、记录定位、长原文偏移，以及关联删除和失败恢复屏障。

## 问题与解决

| 问题 | 处理 |
| --- | --- |
| 连续 TTS 仍可能卡住 | 拆分发送/播放职责，并使用已有组件分离发送锁，而不是无限增加 PCM |
| “第二个方案”在分步骤解释后指错 | 区分候选方案和解释步骤，保留选择与版本 |
| 修改限制后旧约束重新出现 | 更新讨论状态，后台整理结果提交前核对版本 |
| 删除一条记忆影响无关对话 | 依据来源、名称、别名和旧值定向清理，失败不报告成功 |

## 检查与遗留事项

当天早期版本在用户提出“不用编译”前有构建/模拟测试记录；后续修正只执行非编译检查，补充的 C 回归用例未运行。此后编译与烧录由用户完成。

需回归较长回答、满队列、短按取消、下一轮隔离、超过六轮追问、重启恢复和删除失败。来源匹配不是无限语义检索；生成、提交 PCM 与实际听到必须分别记录。
