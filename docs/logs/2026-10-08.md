# 2026-10-08｜重新梳理语音链路与内存分工

## 今日目标

连续几轮修改后，语音仍出现请求失败、误打断和设置反馈不一致。我决定先整体梳理资源与流程，不再把所有异常都归为同一个“内存不足”。

## 遇到的问题

- 唤醒词已经命中，但 UI 锁或设备状态变化使唤醒请求被丢弃。
- 更改主页已保存，后续播报却失败，界面把整轮都显示为失败，掩盖了实际执行结果。
- TTS 连接阶段出现内部 RAM 紧张；另一些失败是域名解析或网络连接错误。
- 回答还在生成时，轻微响声就让设备切回聆听，普通 VAD 对“谁在说话”判断不够可靠。

## 调整与取舍

我把动作执行、回答生成和音频播报的结果分开看待，检查唤醒到 UI/语音协调的完整路径。内存上区分内部 RAM、PSRAM 和 SD：大缓冲交给 PSRAM，SD 只做持久记录，不能拿来补实时 RAM。

游戏内容先备份，再从当前固件移除；优先保留桌面和语音。网络与语音连接的资源峰值、后台作业以及取消清理顺序一起调整，逐步收敛到先完成 LLM、释放连接、再启动 TTS 的流程。

## 检查与边界

当日截图提供了 ESP_ERR_NO_MEM、域名解析失败、状态丢弃与误打断等不同证据。它们需要分别处理，不能用一项阈值调整解释全部现象。源码与主机检查不替代实机听测。

## 后续安排

固定版本与测试场景，继续观察播报中回声、误暂停和下一轮输入。后续实际效果按下一天日志记录，不把本日修改直接写成稳定修复。
