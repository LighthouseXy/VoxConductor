# 技术架构与实现路线

更新：2026-10-11。这里描述我当前开发版的设计与实现。GitHub 本批发布硬件、文档和演示资料，最新固件另行发布；复现需使用与本文对应的代码和配置。

## 1. 系统分工

我将设备定位为“具备本地交互和执行能力的云端语音终端”，不是在 MCU 上运行大模型。ESP32-S3 负责实时外设、界面、状态机、参数校验和持久存储；云端分别完成语音识别、文本生成和语音合成。设备可独立联网使用，无需电脑常驻 FastAPI。

| 层次 | 实现 | 工程重点 |
| --- | --- | --- |
| 电路与结构 | 四层定制 PCB；数字麦克风、I2S 功放、SPI 屏幕、SD、I²C 姿态传感器；棱镜和打印结构 | 电源分配、接口方向、音频输入输出与装配包络 |
| 驱动与交互 | ESP-IDF 6.0.2、FreeRTOS、LVGL 9；按键事件与倾斜手势 | 输入语义一致、界面锁与业务执行分离 |
| 本地声学 | ESP-SR WakeNet；空闲唤醒与播放期间 AEC 后的关键词检测 | 连续音频帧、模型输入幅度、参考时序、代次隔离 |
| 云端对话 | 实时 ASR WebSocket → DeepSeek HTTP → 实时 TTS WebSocket | 超时、取消、连接生命周期和结果状态 |
| 设备工具 | 模型函数调用、本机快捷命令、白名单执行器 | 参数校验、确认规则、实际回执而非模型口头承诺 |
| 数据与管理 | PSRAM 缓冲；SD 原文、双槽快照；同网 HTTP 管理网页 | 有界容量、写入校验、失败可见和媒体事务恢复 |

屏幕通过 SPI2 驱动，SD 使用 SPI3；麦克风与扬声器分别使用 I2S 输入和输出。各接口独立不等于没有资源竞争：CPU、内部 RAM、任务优先级及 DMA 都会影响连续音频。具体 GPIO 见 [板级接口](HARDWARE_V1.md)，器件数量见 [电子 BOM](../hardware/BOM.md)。

## 2. 从唤醒到回答

1. **进入对话**：空闲时本地检测“小冰小冰”，或用实体按键发起。空闲音频不上传云端；只有被接受的语音轮次进入采集流程。
2. **录音与 ASR**：16 kHz、16 位单声道 PCM 采集并上传至实时识别服务。自动模式用讲话与静音结束判据，按键模式由松开结束；超时和取消均有明确终态。
3. **路由与工具**：完整转写先经过受限本机命令，再进入模型。模型以 `tool_choice=auto` 选择查询或操作，设备执行器独立判断参数和权限。
4. **生成最终文本**：工具结果交回模型；每轮最多两次工具往返、四次工具调用。模型连接释放后，才分配 TTS 会话，减少内部 RAM 峰值。
5. **接收与播放**：24 kHz、16 位单声道 PCM 进入 PSRAM 环形缓冲，经音量缩放和 I2S 输出。当前队列 384 KiB、首次预缓冲 24 KiB；底层 DMA 为 8 × 256 帧，约 85 ms 的输出容量，不等于增加同等问答网络延迟。
6. **结束与接话**：记录成功、失败或取消，并保存有界上下文。正常回答后提供 12 秒续问窗口；无讲话则退出。完整结束短语在 ASR 后本地处理，按键仍可立即取消。

语音识别、大模型和 TTS 都需要网络。天气查询复用后台缓存，不让模型凭空生成“实时”数据；结果包含有效性和时间信息。当前位置默认杭州，空气质量用 US AQI，与中国 AQI 不混用。

## 3. 工具调用如何落到真实设备

设备工具是固件内的受限函数调用接口，**不是通用 MCP 服务端**。自然语言理解由模型承担，关键动作仍由设备确定。

| 阶段 | 设备行为 |
| --- | --- |
| 判断意图 | 区分查询、设置与普通问答；精确本地短语可跳过模型 |
| 校验参数 | 检查范围、日期、任务 ID、目录中的实际文件名；不接受任意路径或猜测文件 |
| 确认操作 | 删除、覆盖及部分任务变更需要下一轮明确确认；授权不从历史或摘要恢复 |
| 执行与保存 | 调用真实设备模块，检查 NVS/SD 结果，区分已接受、已应用、已保存和延后执行 |
| 组织回答 | 将回执交给模型；播报失败不撤销此前已成功执行的设置，也不能伪装为动作失败 |

例如调整音量要核对当前设置值和保存结果；恢复钟表主页修改的是主页类型，不需要删除壁纸。媒体操作的回执代表设置应用，不代表扬声器已经完整播完文件。

## 4. 实时音频与资源控制

我采用“一位轮次协调者负责对话生命周期”的方式管理采集、工具、取消、播报和接话。打断请求关联当前播放代次；旧回答停止并释放资源后再交接下一轮，避免旧网络数据或状态回调写入新轮次。

播放中唤醒词打断与空闲唤醒是两条声学路径。前者需要用实际送出的扬声器 PCM 作为回声参考，再将处理后的麦克风音频送入关键词模型。因此，参考缺样、声学耦合、饱和削波和调度间隙都可能影响识别，不能仅靠降低阈值解决。

大块音频、文字和显示缓冲优先使用 PSRAM，内部 RAM 留给 DMA、任务栈和网络连接。PSRAM 空闲很多不代表内部连续内存足够；SD 是持久介质，也不能替代 DMA 内存。TTS 补缓冲次数、I2S 写入时长、队列余量和参考缺样分别记录，用来区分网络供给不足与本地调度卡顿。

当前已经有成功打断记录，但播报连续性、回声混入和新问题完整性仍需系统回归，我不把它描述为稳定全双工。

## 5. 持久存储与网页管理

近期上下文最多 6 对，长期记忆最多 16 条，任务最多 8 条。SD 按轮次保存用户原文、生成回答和终态；回答“已生成”不等于“已完整播放”。快照使用双槽、校验和读回，较新槽损坏时回退有效旧槽；这不能保证介质损坏时恢复全部数据。

管理网页复用设备状态与业务模块：轻量状态 GET 不读取历史文件；设置和任务通过有界作业执行；媒体命令通过有限回执查询结果。上传先写 `.part`、校验，再替换正式文件，并保留 `.old` 进行失败恢复。浏览器取消传输不保证撤回已完成的文件提交。

网页是同网管理入口，不是公网服务。当前不需要配对码，页面不读取云端密钥；使用范围与接口见 [网页设计与验收](WEB_MANAGEMENT_DESIGN.md)。

## 6. 如何证明实现有效

我把证据分为源码检查、主机测试、固件编译、设备运行和重复实测。视频展示一次功能过程，不能代替唤醒成功率、延迟统计或长时间稳定性。回归同时核对屏幕、串口轮次、设置回读和实际声音，保留失败记录。
